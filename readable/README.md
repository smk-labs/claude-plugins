# readable

Easy-to-read outputs from Claude: four small tools, one goal.

## 1. RTL cards (automatic)

Chat clients lay plain text out left-to-right, so mixed Persian/English replies scramble: trailing periods jump to the head of the line, Latin tokens reorder, numbers flip. One fix patches the app itself ([claude-rtl](https://github.com/smk-labs/claude-rtl)); this one fixes Claude's replies with no app changes.

A `SessionStart` hook injects one short rule: reply in Persian as a single self-contained widget card. The model writes its answer as HTML plus a fixed `<style>` kit (Vazirmatn font, per-block direction resolution via `unicode-bidi: plaintext`, LTR-isolated code and paths, accent headings, framed tables, callouts, check/cross status lists). The kit is constant CSS the model copies verbatim, never invents, so polish is nearly free: styling is defined once and the model only spends class names (`ok`, `tip`, `note`, `warn`).

Since 6.0.0 delivery is not a setting, it is a consequence. The `SessionStart` rule names three tiers and the model picks by what is in its own tool list:

1. **card** — a `card` tool is listed, so the MCP Apps card server is connected (section 3). Content-only HTML, styling once in the server template.
2. **widget** — no card tool, but the host has a widget tool. The model reads [hooks/kit.md](hooks/kit.md) on demand and renders the same blocks itself. The kit is a path in the rule, not an injection, so a session that never reaches tier 2 pays nothing for it. [hooks/kit-inline.md](hooks/kit-inline.md) is the same kit with every byte inline, for a host with no network.
3. **text** — neither is listed. English plain; Persian and any RTL written BiDi-safe. Not a failure state: the correct output when nothing on the host can render.

The server enforces tier 1 from its own side. A host that did not negotiate MCP Apps is not offered the `card` tool at all, and a call to it is refused rather than answered. Through 5.x such a host got the tool and a successful result that merely *said* it had not rendered, so the HTML rode `structuredContent` into the transcript as raw markup while the model signed off with "card delivered above" over a reply nobody saw. An error cannot be mistaken for delivery; a note can.

Persian/RTL always gets a card in tiers 1 and 2; English conversational and structured answers do too (code-heavy replies stay plain text; the extra cost of an English card is just HTML tags vs markdown, roughly 10-20% of content).

The inline kit is pay-per-use since 3.2.0. Every widget card carries a small BASE block (~2.5 KB: card frame, headings, text, lists, callouts, code). Components (table, badge, kv, kpi, bars, spark, donut, flow, timeline, cta, since 4.19.0 card/box, cols, blockquote, src, numbered, and since 5.5.0 hub/hub tree) each have their own snippet the model appends only when the reply actually uses them. A prose answer costs about a quarter of the old fixed kit; a full dashboard still costs less than the old kit did.

Since 4.20.0 the card template is pay-per-use too, and by a different mechanism. The template cannot be tailored per card — a `ui://` resource is predeclared and served static, before any card content exists — so the tailoring moved off the template: it now carries BASE only (25.9 KB of the 30 KB ceiling, flat forever), and the app asks the server for the component snippets a given card's HTML actually needs. `server.js` parses the `@TAG` markers into a tag map with per-component detectors and dependencies, and the app-only `read_kit` tool returns just those snippets, which the bridge mounts as `<style id="rckit">` before the first paint. A prose card gets 0 bytes of component CSS; a kv+badge card gets 592; a full dashboard gets ~2.5 KB — all on the tool-result channel, like the base64 font bytes `read_fonts` already returns, so none of it counts against the resource ceiling.

Three consequences. The 30 KB ceiling is off the critical path for good, so a new component no longer has to win a byte auction — 5.0.0's icon set is the proof: 16 Lucide-style glyphs as a single inline SVG sprite behind a CSS mask, painted with the brand accent (one colour for the whole set) and sized from the surrounding font, so they read as markers rather than letters, with no font file, no request and no JS. Under the old inlined sheet a ~2.5 KB component could never have shipped; delivered per card it costs nothing unless a card uses an icon. 5.1.0 adds `figure` the same way: a screenshot, a diagram, or a looping `/fig` animation, with `build.py` inlining every local `<img src>` as a `data:` URI (2 MB per image by default, `--max-image-kb` to raise it) so a report stays one offline file that survives being emailed or printed. A `/fig` .html has its `<svg>` lifted out with the document's `<style>` folded in, so it animates inside `<img>` and stays isolated from the report's own cascade. 5.2.1 took that path seriously: once embedded, the svg is a separate document, parsed as strict XML, running no script, inheriting no direction — so the build now validates the XML and refuses on a parse error naming the file, line and column, folds every document `<style>` (not just when the svg lacked one of its own), carries the figure's own text direction onto the `<svg>` so a Persian figure's labels keep their anchors, and warns when a figure's only motion is JavaScript. 5.3.0 finished the list: the embedded svg gets no page FONT and no network either, so a brand font declared as `font.google` (which 5.2.0 declared and never loaded) is fetched and inlined at build time, and the report's own face is folded into each figure, subset to the characters that figure letters. `--inline-figures` writes figure markup into the document instead of a `data:` URI, which is what survives a host CSP that omits `data:` from `img-src` or a sanitiser that strips `<style>` from an svg; the lift namespaces the figure's classes and ids to pay for the isolation `<img>` used to give. Same release: `td`/`th` moved from `unicode-bidi:plaintext` to `isolate`, so an RTL table column stops rendering ragged when one cell happens to open on a Latin token. Full account in [CHANGELOG.md](CHANGELOG.md). Images are a report feature and the chat rule deliberately says nothing about them: a card cannot carry image bytes through the model's context cheaply, and the report skill states plainly that the default is no image. Every component now reaches a chat card when the content genuinely uses it, which is why `@REPORT` is now only a tier divider telling the rule authors what not to advertise, not a CSS cut. And the card stays offline-safe, because the CSS comes from the local MCP server rather than a CDN — the alternative (`@import` from jsDelivr) would have left an offline Persian card unstyled, which is unreadable rather than merely plain, since BiDi ordering depends on the kit. Failure is graceful and bounded: an error or empty reply paints on BASE alone, and a host that never answers is capped by a 1.5s deadline after which a late reply still mounts and restyles in place.

The card is self-contained by default: components degrade to plain readable text if their CSS is missing, and nothing depends on the network except the font import, which falls back to system fonts. Note: a live probe (2026-07) showed the widget sandbox is an `https://*.claudemcpcontent.com` iframe that DOES run inline scripts and CAN load external stylesheets, fonts, and `fetch()`. Self-contained stays the default for offline safety, but that finding enables the hosted variant below. (`PreToolUse` hook rewrites of `widget_code` are still ignored by the renderer; only what the model itself emits counts.)

Everything adapts to light and dark mode through the host's CSS variables.

### Diagrams: hub and hub tree (5.5.0)

The kit could draw a sequence (`flow`), a chronology (`tl`) and a comparison (`cards`), but not one thing connected to many, so authors faked that with a bullet list. Two components close it, and both are CSS only: no JS, no SVG, no image.

`hub` is a centre with up to eight legs, each leg an arrow that carries direction of flow. `out` on a leg turns its arrow around, which is the whole difference between "reads from" and "writes to", so the diagram keeps one hue instead of buying a second colour to say the same thing. Markup stays flat, the same shape as `flow`:

```html
<div class="hub">
  <div class="c">باقرزاده<span>پلاگین جامع شرکت</span></div>
  <div class="s">نوشن<span>هاب ایجنت‌ها</span></div>
  <div class="s out">دیسکورد<span>با کران خبر می‌دهد</span></div>
</div>
```

It is a 3x3 grid. `.c` takes the middle cell, the eight `.s` auto-flow into the ring around it, and each slot declares only where its leg starts on its own box, which way it runs and how long. The corner legs are 45 degrees because the row gap equals the column gap, so a corner cell's inner corner sits the same distance across in both axes and the leg lands on the centre cell's corner with nothing measured. Anchoring on the box rather than on the hub centre is what makes that exact: cells are wide and short, so a 45 degree ray from the middle misses the corner cells completely. RTL costs one sign flip, because every angle is read in the inline frame rather than in physical left/right.

`hub tree` is the same markup plus `tree`: a root, branches and leaves, no arrows, because a branch means "groups", not "moves toward". A branch may nest its own `.s` children, which render as a connected group inside it. Nine items or more wants the tree, not the hub, because the ring holds eight.

Both reflow to one column below 520px and never scroll sideways, both nest inside `card` and `box`, and both print with their connectors intact, because every connector is a border and `print-color-adjust` keeps borders when it drops backgrounds.

### Long documents: tabs, preview, sections (5.6.0)

Three components out of one real report, a long decision document with three parallel options. A reader could not move between the options, the links out to related documents looked like a spreadsheet row, and the sections did not read as separate.

`sections` is one class on the same wrapper `numbered` already takes: `<div class="numbered sections">`. Every direct-child `h3` then gets a hairline rule above it, room to breathe and one size up. The two compose with nothing reconciled, because the section number lives on `h3::before` and `sections` touches only the box.

`preview` is a link to another document drawn as a document: `<a class="preview" href><b>title</b><span>context</span><small>host</small></a>`, with `build.py` writing the host in off the href. Optionally a live scaled-down frame goes under it, `<div class="preview live"><iframe></div>`, as a SIBLING rather than a wrapper — which is what makes the fallback free, since a target that refuses framing simply loses the frame and the card is already there. That refusal is decided at build time because runtime cannot know: a frame blocked by `X-Frame-Options` still fires `load`, its document is cross-origin either way, and a `file://` report cannot fetch the url to look. `build.py` reads the headers, treats unreachable as refusing, and names what it dropped. The frame renders at `1/--s` of the container and scales back by exactly `--s`, so a desktop page reads at report width; below 520px `--s` is 1 and the target shows its own narrow layout at full size. A transparent lid keeps the wheel on the report.

`tabs` is a pinned bar over the sections: `<div class="tabs"><a href="#p1">label<span>sub</span></a>…</div>` against `<h3 id="p1">`. Report tier, because a chat card has no scroll of its own. The bar, the jump and the landing offset are CSS, so it degrades to plain anchors; only the follow-on-scroll highlight is script, in the report shell and guarded so a report without a bar runs nothing. Two traps are pinned by tests: the scrollspy never runs through `requestAnimationFrame` (throttled to zero in a hidden tab, which freezes the bar), and the bar's height is measured rather than hardcoded — it wraps, and a fixed offset then parks the jumped-to heading behind the bar's second row. It is measured with a `ResizeObserver`, since the webfont lands after first paint with no resize event to hear.

### Token cost

The style kit used to ship in full with every reply; now replies pay only for what they use.

- Old (<= 3.1.x): ~9.2 KB CSS ≈ 2,550 output tokens per card, every card.
- New BASE only (prose replies, the common case): ~2.5 KB ≈ 700 tokens.
- New worst case (all snippets): ~7.3 KB ≈ 2,000 tokens.
- Hosted variant (below): BASE + one `@import` line regardless of components used.

### The tier 2 kit

[hooks/kit.md](hooks/kit.md) is what the model reads when it lands in tier 2. BASE stays inline as the offline floor; component CSS arrives on one line, `@import url('https://cdn.jsdelivr.net/gh/smk-labs/claude-plugins@main/readable/assets/rc.css')`. [hooks/kit-inline.md](hooks/kit-inline.md) is the same kit with every component inline, for a host with no network at all.

Both files are **generated** (6.7.0): `node readable/tools/gen-kit.js` writes them from `assets/rc.css` plus the block vocabulary in `assets/blocks.md`, and `--check` fails the test run if either is stale. They were hand-written for six releases and it showed — kit.md's BASE was missing the whole `<pre>` block and still carried a `code` rule that had moved, and its CDN line was pinned to `readable-v6.4.1` while the plugin shipped 6.6.0, so tier 2 was quietly painting with two-release-old CSS.

Two things about that URL. The path is `readable/assets/...`, not `plugins/readable/assets/...`: plugins sit at the repo root here, so the `plugins/` form was a 404 that failed silently as an unstyled card. And the ref is `@main`, which reverses the 6.0.0 note that argued for a release tag. The argument for a tag is real — on a branch a push restyles cards already rendered elsewhere, and jsDelivr takes ~12 h to agree about what the branch now says. The argument against it is the release history: the tag was bumped by hand, so it lagged by two releases in `kit.md` and by six in this README, and tags for 6.5.1 and 6.6.0 were never pushed at all. A tag ref that names an unpushed tag 404s, and an unstyled card is a worse failure than an old card restyled. The generator removes the drift either way; `@main` also removes the 404.

### Voice: how the words are written (6.9.0), and what it draws (6.10.0)

Everything above is layout. This is the sentences inside it, and it applies at every tier, cards or plain text.

The `SessionStart` rule now names two style files and tells the model to read the one it is about to write in:

- [hooks/voice-fa.md](hooks/voice-fa.md) — plain, concise Persian. Anti-translationese, anti-officialese, anti-padding: no `می‌باشد`, no `لازم به ذکر است`, no invented Persian equivalents for terms nobody says out loud, no em dashes, no emoji.
- [hooks/voice-en.md](hooks/voice-en.md) — the English equivalent: cut the AI tells, then put a voice back in.

`voice-fa.md` is generated from the [gouya](../daily-tools/skills/gouya) skill in daily-tools — one document, two delivery paths, so readable ships the voice standalone without depending on daily-tools being installed. `voice-en.md` is [unslop](https://github.com/cursor/plugins/tree/main/pstack/skills/unslop) from cursor/plugins, vendored with one clearly marked section added; that repo carries no LICENSE file, so it is an attributed copy rather than a licensed one.

Both carry the same third principle alongside plain language: **a picture is worth a thousand words.** Content that has a shape gets drawn, not described. Three paragraphs walking through steps is a flow nobody drew; a bulleted list of a system's parts is a hub with its connections thrown away. The voice files state the principle in the reader's own language and stay medium-neutral, because gouya is also used over plain files where no component exists. The operative half lives in the `guidance` section of `assets/blocks.md`, which is the one channel that already ships to every card and can name real components — `hub`/`hub tree` for a system, `kpi`/`bars`/`spark` for numbers, `flow`/`tl` for sequences. That mapping costs 48 tokens on the always-loaded description, which is the whole input-token price of the principle. The guard against the obvious failure is in the same sentence: the limit is decoration, not restraint, and a two-line answer still gets zero components.

They are **named, not injected**, for the same reason the tier 2 kit is. Together they are 16 KB, and most of that is whichever language the session never types. Inlining both would cost about 4,400 tokens in every session to make roughly half of it useful — the same bill 6.6.0 spent a whole release removing from `rule.md`. The pointer costs ~100 tokens; the file that gets read costs ~2,300 (fa) or ~2,100 (en), once, and only in a session that actually writes that language. `server/test.js` asserts the hook names both and inlines neither, and caps the whole SessionStart payload, so a later edit cannot quietly paste one in and call it "always applied".

### Architecture

One design system, four places it can be delivered, and every fact about it written down once.

- **Single sources**, all under `assets/`: `rc.css` (the sheet, `@TAG`-marked per component), `blocks.md` (the block vocabulary), `palette.css` (colours), `ltr.css` (the English overrides), `fonts.json` (the web-font fetch policy), `menu.js` and `email.js` (shared behaviour). Each is read by every path that needs it, JavaScript and Python alike, with at most one documented adaptation at the point of use.
- **Server modules** in `server/`, each one thing: `kit.js` is the only code that parses `rc.css`; `blocks.js` assembles the vocabulary per tier; `theme.js` adapts palette + LTR for a card; `template.js` builds the `ui://` resource; `bridge.js` is the iframe's script; `brand.js`, `files.js`, `fonts.js`, `sys.js`, `host.js`, `paths.js`, `rpc.js`, `tools.js`. `server.js` is wiring only.
- **Tools are data**: one registry entry per tool (schema, `needsUi`, `failure` prefix, `run`), one dispatcher. Bad arguments are always a protocol error, never a successful-looking result.
- **Generated, not typed**: `tools/gen-kit.js` writes both tier 2 kits. `test.js` proves the sheet, the vocabulary and the detector table describe the same components, and that no palette, LTR rule or font constant has been copied anywhere.

## 3. card MCP server (experimental, opt-in)

The endgame for token cost: the model sends only content and never outputs CSS at all. [server/server.js](server/server.js) is a zero-dependency MCP Apps server (SEP-1865) with one tool, `card`: input is building-block HTML, and the host renders it inside a predeclared `ui://readable/card.html` template that carries the whole kit plus its own light/dark palette (host CSS variables do not reach inside the MCP Apps iframe).

- Protocol-tested: `node readable/server/test.js` runs a 317-check JSON-RPC exchange, including capability negotiation (`io.modelcontextprotocol/ui`), the `roots/list` save-dir handshake, template mime `text/html;profile=mcp-app`, `_meta.ui.resourceUri` linkage, and the no-UI-host fallback (tool answer tells the model to fall back and re-deliver as text/widget).
- Template-tested: the bridge (`ui/initialize` → `ui/notifications/tool-input` → `ui/notifications/size-changed`) renders the card correctly in a sandboxed iframe; CTA buttons map `sendPrompt()` onto `ui/message`.
- Production-verified (2026-07): Claude Desktop chat negotiates `mcp-apps=YES` for local servers and renders the card inline, light and dark.
- Re-learned in 6.4.0, the hard way: the 4.5.0 note below was right and 6.0.0 broke it. 6.0.0 declared a plugin-scoped copy of the server, reasoning that the new capability gate made a duplicate harmless. It did not. The card call stopped reaching the desktop server (its log showed a healthy `mcp-apps=YES` handshake and no `tools/call card` at all) and the html printed raw in the chat, exactly as this note warned. The scoped server is now named `readable-local` and runs with `READABLE_NO_CARD=1`, a hard no checked before anything a client declares, so it carries the export tools and can never be handed the card tool by any host. When a note in this file says "field-debugged", read it before overriding it.
- Since 4.5.0 the plugin does NOT register the server itself. Root cause (field-debugged 2026-07): only the desktop app's own MCP client (`claude_desktop_config.json`) negotiates MCP Apps; servers spawned by the Claude Code CLI (plugin `mcpServers`, project `.mcp.json`, user scope) connect as `client=claude-code, mcp-apps=NO`, so their cards render as raw tool rows inside the grouped-tools container. Worse, a duplicate registration exposes two same-named `card` tools and the model picks one at random, which surfaced as "the widget sometimes does not render". One registration, the right one: `claude_desktop_config.json` (global to every project's desktop session); with multiple profiles, [claude-sync](https://github.com/smk-labs/claude-sync) v2.2+ propagates that entry everywhere.
- File mode (4.6.0): `card` also accepts `htmlFile` — an absolute path to a pre-written `*-card.html` file — instead of `html`. Built for delegated/background workers (e.g. the cursor-delegate plugin): the worker authors its own report card on its own quota, and the main agent renders it with one ~50-token call. The HTML never enters the model's context in either direction: the args carry only the path, the result's `structuredContent` carries only the path (the desktop host echoes `structuredContent` back to the model verbatim — measured), and the template bridge pulls the actual content itself through the app-only `read_card_file` tool over host `tools/call`, the same channel the Email export uses. Guardrails: absolute path, `-card.html` suffix, 256 KB cap, same no-`<style>`/`<script>` rule.
- Email export that email clients actually run (5.4.0): the export used to hand the client the same markup and class names the card uses on the web, and email clients are not browsers — Gmail strips `<style>` on forward and reply, Outlook on Windows renders through the Word engine. Custom properties, grid, flex, `::before`/`::after`, `color-mix()`, `:is()` and logical properties are all unsupported, so a card that reads as a dashboard on screen pasted into a mail as a run of naked text with the numbers in the wrong order. Pseudo-elements were the worst of it because they fail silently: a list keeps its text and loses its bullets, and a `numbered` document loses every section number with no way back, since counters were never characters. There were also two adapters — a server-side style map and a report-side `getComputedStyle` walker — and they had drifted. Now one transform in [assets/email.js](assets/email.js), shared by both hosts, emitting table-based inline-styled HTML with literal colours: every grid/flex component becomes a `<table>` (cells carry `align=`, which Word reads, and every table its own `dir`, which Word resolves per table), every pseudo-element decoration becomes a real character including the Persian section numbers, a `fold` exports already open, a donut ships its legend numbers, a `data:` figure falls back to its caption, and a branded card finally exports in its own colours instead of the kit blue. One test renders a card using every component and asserts the output contains none of `var(--`, `display:grid`, `display:flex`, `::before`, `::after`, `color-mix(`, `:is(`, `inset-inline`, or any `class=`.
- Card menu (4.1.0): every card carries a three-dot menu styled after the host's code-block popover, entirely template-side (zero output tokens per reply): Copy image (hand-rolled foreignObject-to-PNG with best-effort inlined fonts), Copy HTML / Markdown / plain text (programmatic DOM-to-Markdown converter), Download PNG, and Save HTML via the spec's `ui/download-file` with `<a download>` fallback.
- Code-block copy (4.11.0): hovering any `<pre>` code block shows a small copy button on its corner that copies that block's plain text, in chat cards and exported reports alike (one shared implementation in [assets/menu.js](assets/menu.js), living outside `#card` so no export path ever sees it). Paid for under the 30KB template ceiling by assembly-time var aliasing: the template copy of the kit shrinks `var(--text-accent)`-class tokens to `var(--ta)`-class aliases defined once on `.rc`; sources and the report/hosted sheets keep the long names.
- Host-first copy (4.11.1): inside the sandboxed MCP Apps iframe, page-level clipboard writes are silently swallowed while `execCommand('copy')` still returns true, so every Copy button showed a false "copied" check (field bug). All card copies now go through the app-only `copy_text` tool: the local server pipes the text into the OS clipboard helper (`pbcopy` / `clip` / `wl-copy`/`xclip`/`xsel`), the same channel saves already use. Browser clipboard stays as the fallback there and as the whole path in standalone reports, where it genuinely works.
- PNG export now embeds the real fonts (4.14.1): an SVG rendered via `Image`→`canvas` cannot load an external `@import` font, so copied/downloaded card images used to rasterize in a system fallback (Vazirmatn → Tahoma) — the reported "wrong font/styles". The fix inlines the actual font bytes as base64 `@font-face`: the card pulls them from a new app-only `read_fonts` tool (the server owns the kit imports and fetches + base64-embeds the used subsets — arabic/latin/latin-ext — once, cached); the standalone report embeds them client-side on load. Mounted as a `#rcfont` style before rastering; offline just falls back to the system font. The template stayed under 30KB by extending the assembly squeeze with one-letter helpers for `createElement`/`getElementById`/`querySelectorAll`.
- The menu really does clear the title now, Persian included (4.17.0): 4.14.0 moved the `⋯` menu to the corner where lines end and claimed both directions. It only ever worked in LTR. `#rcmenu` sets `direction:ltr` on itself so its own dots and labels never mirror, and a logical inset resolves against the element's OWN writing mode, so `inset-inline-end` was always the physical right no matter what the card said. Proof: setting `document.documentElement.dir` to `rtl` did not move the dots by a pixel. Measured in Chrome against the real `ui://` template at a 1034px card, the dots sat at x=996..1026 while even a short Persian title reached x=1012, so the menu covered the first characters of the heading on every RTL card. The side is now read from the card itself: physical `right:8px`, flipped by `#card[dir=rtl]~#rcmenu{left:8px;right:auto}`, with the dropdown panel flipped to match so a left-side menu opens inward instead of past the viewport edge. Same measurement after the fix: RTL dots at x=8..38 against a title running 679..1012, LTR untouched at 996..1026. The standalone report carried the same bug in its own inline override (`inset-inline-end:62px` on that same `direction:ltr` element): a Persian report puts the theme toggle on the left and the Copy/PDF bar on the right, and the dots landed 28px on top of the Copy button. The report shell now reads its side off the ROOT dir instead, so the menu stays beside the theme toggle in both directions; English reports are geometrically identical to 4.16.0. Costs 75B of the 30KB template ceiling (29641B) and is pinned by five new checks, including the first ones to cover the report shell at all, which is why the report half went unnoticed for two releases.
- Export controls ride the pointer (4.16.0): a tall card used to be exportable only from its top. The chat host grows the card iframe to the WHOLE card and that iframe never scrolls, so `position:fixed` pins to the card, not to the app window — scroll the chat down and the `⋯` menu was stranded far above. Nothing inside the frame can read the app's scroll offset, but the pointer implies it: whatever the pointer is over is on screen. So the menu now glides to the pointer's height while the pointer rides either vertical edge (the reading area is left alone, so nothing twitches while you read), and each `<pre>`'s copy button follows the pointer down its own block's edge instead of clinging to the block's top — in a scrolled report that button used to sit at viewport `-177px`, off screen and unclickable, while you hovered the block's visible middle. Both center on the cursor, which is what stops them running away as you reach for them. Paid for under the 30KB ceiling by extending the assembly squeeze with a `querySelector` helper and an anonymous-`function`→arrow pass (neither source uses `this` or the `arguments` object), which freed 633B.
- Registration is automatic, once, everywhere, and reversible (6.1.0): [hooks/connect.sh](hooks/connect.sh) is the only file in the tree that names a desktop config, and the only copy of the profile list. `auto` runs from the session hook and is what makes the plugin plug and play; `connect`, `disconnect` and `status` are the same code path for a human. 4.15.0 through 5.6.1 also wrote automatically but knew one profile path, backed up on every write, said nothing, and undid your removal on the next session; 6.0.0 fixed those by refusing to write at all, which cost readable the reason it exists. 6.1.0 keeps the automation and fixes the four defects, each pinned by a test against a fake HOME with four fake profiles.
- The clipboard speaks UTF-8 (5.7.0): the server is started by a GUI app, which passes down no locale at all, and macOS tools read a locale-less environment as Mac OS Roman. So `pbcopy` took correct UTF-8 bytes and transcoded each one into its own MacRoman glyph: copying a Persian card put `ŸÖÿ≥ÿ™ŸÜÿØ` on the clipboard where `مستند` was written. Every child process now gets `LC_CTYPE=UTF-8` and an explicit UTF-8 buffer, which also un-mangles the Persian default filename in the save panel and the path it hands back.
- Windows copy fixed + menu never covers the title (4.14.0): the Windows `clip.exe` path fed UTF-16LE with a leading BOM, so every copy was pasted with a stray zero-width `U+FEFF` beside it and Persian snippets looked mangled — the BOM is now dropped (bare UTF-16LE). The `⋯` menu also moved off the top-right corner toward the corner where lines end, so it stops covering the title and brand logo that anchor where lines start. It was built on `inset-inline-end`, which turned out to move the menu in LTR only; RTL cards were not actually fixed until 4.17.0 above.
- Downloads that land where you work (4.12.0): card downloads open the native macOS save panel (osascript `choose file name`) defaulting to the session's project root — the server asks the client for MCP `roots` and prefers the first one over `~/Downloads`; `READABLE_SAVE_DIR` skips the panel. The `save_card` RPC ACKs (`picking: dir`) before the dialog opens so the card UI never waits on the user. Exports are named after the card title (first `<h2>`, Persian preserved, spaces to dashes) instead of `readable-card.*`. Every menu RPC now carries a deadline: hosts that silently drop `tools/call` (no response at all — the field bug that made all five download buttons hang forever on a spinner) fall through to `ui/download-file`, then to `<a download>`. The email rich-copy dropped its `execCommand` fallback for the same honesty reason as 4.11.1.
- Small-model note (Haiku): tool descriptions alone do not reliably steer small models, and Desktop chat has no hooks. The fix there is one line in your Claude profile preferences (Settings → Profile): "For every Persian/RTL reply, and preferably for structured English replies, call the readable-card `card` tool with the entire reply as building-block HTML; the tool call is the whole reply."

## 4. report (skill, explicit export only)

Turns a chat card (or fresh content) into a standalone HTML report file in the exact same template, without the model ever writing CSS: the model writes content-only HTML, and [skills/report/build.py](skills/report/build.py) injects the kit from `assets/rc.css` into a page shell (light/dark toggle, print styles for PDF). Persian is RTL with Vazirmatn; `--lang en` gives the same design fully LTR with Inter (arrows and alignment auto-flip). The report carries two one-click buttons (4.14.0): Copy (the card text, through the same clipboard bridge the menu uses) and PDF, which prints the rendered page — a standalone report is a real document, so the browser's Save-as-PDF is exact. (The chat-card menu deliberately has no PDF button: `window.print()` inside the sandboxed MCP iframe would print the whole host app, not the card, so PDF belongs on the exported report.)

Triggers ONLY on an explicit ask ("همین کارت رو ذخیره کن", "save this card as a report") or `/readable:report`. Generic "write a report" requests never trigger it, by design.

## 5. brand (skill, per-project skin — 4.13.0)

`/readable:brand` gives a project its own look: it detects the identity from the repo (design tokens, tailwind config, DESIGN.md, logo SVGs) or interviews the user when none exists, then writes a committable `.readable/` dir at the project root — `brand.css` (palette variable overrides, light + dark, in the kit's own vocabulary), optional `brand.json` (wordmark, header caption, tone word, fonts) and `logo.svg`.

From then on, in that project: `/report` reskins automatically (palette, logo/wordmark header, brand fonts inlined into the standalone file), and chat cards reskin too. Since 4.14.0 a logo/wordmark also becomes a letterhead ABOVE chat cards, not just reports: `read_brand` folds a `.rc::before` rule into the brand css (runtime only, so it costs the 30KB template nothing), rendering the wordmark as pseudo content and the logo as a data-URI — a `currentColor` mark tints via `-webkit-mask` and theme-flips, a colored mark keeps its own colors. Like the report header, the letterhead is invisible to card exporters. Cards work through three resolution paths, most-reliable first: an explicit `brand` param on the `card` call (the `SessionStart` hook announces the dir per project — required in ccd, which spawns the direct server with neither the project cwd nor `roots`), the client's MCP `roots`, or a bounded walk up from the server's cwd (plugin-spawned CLI servers inherit the project dir, so CLI cards brand with zero model involvement). The css travels through the app-only `read_brand` tool — same channel as `htmlFile` — so it never enters the model's context; a dangling or invalid brand silently degrades to the stock look.

Limits, honestly: already-rendered cards don't re-brand; hosted Claude Desktop (.mcpb) has no project concept and stays stock; card fonts only via Google Fonts (the ~30KB template can't embed font files — reports can and do).

## 6. signature (5.2.0)

Every artifact readable produces closes with one muted line: `created by readable · github.com/smk-labs`. It is defined ONCE, on the `@sig` marker inside [assets/rc.css](assets/rc.css), and every path reads it from there — `server.js` freezes it into the card template at assembly time, `build.py` appends it to a report, decode's `build.py` fills its own footer slot from the same marker. It never enters the model's context and costs nothing per session; the only hand-kept copies are the two inactive `rule-*.md` fallbacks, where the model is the assembler and there is no build step, and `server/test.js` asserts those stay byte-identical.

It mounts as the last child of `.rc`, not in the page chrome, and that placement is the whole trick: every exporter in [assets/menu.js](assets/menu.js) serializes `#card`, so PNG, HTML, Markdown, plain text and email all carry it with no per-format code. It degrades by itself, because the link TEXT is the bare domain: markdown gets a real link, HTML/report/email get the real `<a href>`, and PNG and plain text get readable text with a usable address. Muted `--text-secondary` at `.8em` above a hairline, aligned under the line ends in both directions, correct in light and dark, and it prints.

A project turns it off with `"signature": false` in `.readable/brand.json` — one committable flag for cards and reports both. It is ON by default even for branded projects; the case for turning it off is a report that goes to a client, where the mark sits under someone else's letterhead. On the card path the flag rides back on the app-only `read_kit` reply (a leading `!`), because that call already gates the first paint, so an opted-out card never flashes a signature and the node is genuinely absent — not just hidden — which keeps every export clean too.

## Install

```
/plugin marketplace add smk-labs/claude-plugins
/plugin install readable@smk
```

That is the whole install. On the first session the plugin copies its server to a version-free stable path (`~/.claude/plugins/data/readable/server/`, immune to marketplace cache-path churn on updates), registers it in **every** Claude desktop profile on the machine, and says so once. Quit and reopen the app after that first session and tier 1 cards are live everywhere. `/readable:connect status` reports where things stand per profile; `disconnect` removes it from every profile and stays removed.

Registering your config automatically is a real liberty, so here is exactly what it does and does not do. It adds one key, `mcpServers.readable-card`, and touches nothing else in the file. It keeps one backup per config the first time it writes that config, never one per write. It writes on the session that adds the key and on no other session, so the steady state costs nothing: a config already pointing at the stable path is not opened for writing at all. A hand-made override that resolves to a real file is left exactly as you set it. And a `disconnect` sticks, because that is checked before anything else runs.

Every one of those is a 5.x defect turned into an assertion in `server/test.js`. 5.x knew one hardcoded profile path, so the default profile got the entry and the rest diverged, which is why people hand-copied whole configs between profiles and spread live API tokens doing it; it left a `.readable-bak` on every write; it wrote in silence, so a user with no cards had nothing to look at; and removing the entry lasted until the next session put it back. 6.0.0 answered all that by making registration a manual command, which fixed the leak and lost the one property readable exists for. 6.1.0 keeps the property and fixes the defects instead.

The reason it can now register everywhere safely is the capability gate: being registered no longer implies being able to paint. A server whose host did not negotiate MCP Apps does not offer the `card` tool at all. That is also why the plugin now declares its own scoped MCP server, which 5.x warned against on the grounds that a plugin-scoped copy cannot render widgets and the model might call it and show raw HTML. It is now physically incapable of being the one that paints; it carries the export tools (`save_card`, `render_email`, `read_brand`, `copy_text`, …) and nothing else, in any Claude Code session, with no setup.

Finding the profiles used to be a list of known shapes, and it failed twice the same way. 6.1.0 covered five and missed three, because a relay setup keeps its data in `~/.claude-<name>/desktop`. 6.7.x then missed a desktop install relocated wholesale — profile under `~/desktop-trial/profile` with `XDG_CONFIG_HOME` moved along with it — so no glob resolved, the hook found nothing and exited silently on every session, and the machine ran in tier 2 for days with no error to look at. 6.8.0 stops guessing first: Claude Code Desktop bundles its CLI at `<profile>/claude-code/<version>/claude` and names that path in `CLAUDE_CODE_EXECPATH`, so the profile hosting the current session is three levels up and cannot be missed. The glob list stays as the fallback for terminal sessions, which have no such variable. Only that exact layout resolves, so a plain `claude` on `PATH` never nominates an unrelated directory, and the suite runs with the variable cleared so a test can never write to a real config.

One honest gap: desktop chat runs no `SessionStart` hooks, so on a machine where readable is installed and no Claude Code session is ever opened, nothing registers itself. Open one Code session once, or run `/readable:connect`.

## Requirements and scope

- A client that runs Claude Code plugins and has the `mcp__visualize__show_widget` tool (Claude Desktop / Cowork). Without that tool, the rule falls back to BiDi-safe plain text.
- No dependencies beyond Node, which the card server needs to run anyway (the setup hook uses the same Node once to write the config entry). No Python, no network.
- readable styles Claude's replies. It does not change how the app renders the text you type; that is what [claude-rtl](https://github.com/smk-labs/claude-rtl) fixes at the app level.
